# Состояние SQLite и события

Черновик к согласованию. Одна база соответствует одному прохождению. `actor.player` — зарезервированный ID игрока. При создании сохранения движок регистрирует его и назначает начальную локацию, переданную при запуске. Для примеров используется `location.demo.entry`.

## Минимальная схема

Начальные значения раскладываются по типизированным структурам в Go. В `state_json` сохраняются все изменяемые поля, например `{"openable":{"is_open":false},"breakable":{"is_broken":false}}`. Статические параметры вроде текста книги движок читает из каталога в памяти. Журнал хранит значимые результаты действий и событий. При загрузке игра читает текущие таблицы.

```sql
PRAGMA foreign_keys = ON;
PRAGMA user_version = 1;

CREATE TABLE save_meta (
    id INTEGER PRIMARY KEY CHECK (id = 1),
    step INTEGER NOT NULL CHECK (step >= 0)
);
INSERT INTO save_meta (id, step) VALUES (1, 0);

CREATE TABLE entities (
    id TEXT PRIMARY KEY NOT NULL,
    kind TEXT NOT NULL CHECK (kind IN ('location', 'exit', 'object', 'actor')),
    type_id TEXT,
    life_status TEXT NOT NULL CHECK (life_status IN ('present', 'removed')),
    state_json TEXT NOT NULL DEFAULT '{}',
    CHECK ((kind = 'object') = (type_id IS NOT NULL))
);

CREATE TABLE placements (
    entity_id TEXT PRIMARY KEY NOT NULL REFERENCES entities(id),
    parent_id TEXT NOT NULL REFERENCES entities(id),
    CHECK (entity_id <> parent_id)
);
CREATE INDEX placements_by_parent ON placements (parent_id);

CREATE TABLE player_knowledge (
    entity_id TEXT PRIMARY KEY NOT NULL REFERENCES entities(id),
    known_step INTEGER NOT NULL CHECK (known_step >= 0),
    discovered_step INTEGER CHECK (discovered_step >= known_step)
);

CREATE TABLE location_visits (
    location_id TEXT PRIMARY KEY NOT NULL REFERENCES entities(id),
    visit_count INTEGER NOT NULL CHECK (visit_count > 0)
);

CREATE TABLE event_log (
    seq INTEGER PRIMARY KEY,
    action_id TEXT NOT NULL,
    ordinal INTEGER NOT NULL CHECK (ordinal >= 0),
    step INTEGER NOT NULL CHECK (step >= 0),
    actor_id TEXT NOT NULL REFERENCES entities(id),
    target_id TEXT REFERENCES entities(id),
    name TEXT NOT NULL,
    rule_id TEXT,
    once_key TEXT UNIQUE,
    payload_json TEXT NOT NULL DEFAULT '{}',
    UNIQUE (action_id, ordinal),
    CHECK ((ordinal = 0) = (rule_id IS NULL)),
    CHECK (once_key IS NULL OR once_key = rule_id AND rule_id IS NOT NULL)
);
```

Внешние ключи нужно включать на каждом соединении до начала транзакции. Хранилище и движок проверяют инварианты, зависящие от нескольких строк и каталога. [Внешние ключи SQLite](https://www.sqlite.org/foreignkeys.html)

- У каждого присутствующего предмета и существа ровно одно размещение. Локации и переходы не имеют строки размещения. Источник и назначение перехода хранятся в его определении.
- Родитель существа — присутствующая локация. Родитель предмета — присутствующая локация, существо или объект с `container`. Перед перемещением движок поднимается от нового родителя до корня и отклоняет цикл. Проверка и запись выполняются в той же транзакции.
- Удаление экземпляра оставляет строку `entities` со статусом `removed` и освобождает его размещение. Контейнер можно удалить только после перемещения или удаления содержимого. Проверка пустоты включает регистрацию его ещё не материализованных детей. История и знания могут ссылаться на удалённые сущности.
- `known_step` фиксирует первое знание, `discovered_step` — первое непосредственное обнаружение. Знание может появиться раньше обнаружения. Наблюдение и активный поиск записывают оба факта, если их ещё нет. Текущая видимость вычисляется при каждом обращении.
- `visit_count` увеличивается при начальном входе и после успешного перехода в локацию. Первый визит использует `first_visit`, последующие — `revisit` при наличии.
- Форму и значения JSON проверяет Go-код. Состояние несовместимой формы диагностируется при открытии сохранения.

## Ленивая регистрация

Регистрация по ID выполняется внутри транзакции.

1. Ищет строку `entities`. При наличии возвращает её текущее состояние, учитывая `life_status`. Начальный родитель для существующей строки не используется.
2. Для отсутствующей строки находит определение в глобальном индексе, собирает начальное состояние и при необходимости инициализирует отсутствующего начального родителя. Родитель должен поддерживать соответствующее размещение.
3. Вставляет строку с защитой `ON CONFLICT(id) DO NOTHING`. Только при фактической вставке создаёт начальное размещение, если оно требуется. При конфликте читает сохранённую строку. Ошибка записи размещения откатывает всю операцию. [UPSERT в SQLite](https://www.sqlite.org/lang_upsert.html)

Для сборки сцены регистрируются локация, её переходы и её непосредственно объявленные объекты и существа. Затем видимое содержимое выбирается по таблице `placements`. При обращении к содержимому контейнера или инвентаря сначала регистрируются его непосредственные дети из глобального индекса, потом читается актуальное размещение детей. Это работает и для контейнера, перенесённого в другую комнату. Регистрация по ID не требует обхода соседних сущностей. Знания появляются при наблюдении, поиске или явном эффекте.

Например, после обновления YAML новый предмет из `objects` при следующей сборке сцены получает собственную строку. Новый предмет в `contents` при обращении к содержимому начинает в указанном контейнере, где бы тот ни находился. Сохранённые предметы сохраняют родителей. Для нового определения, цепочка начальных родителей которого упирается в удалённого предка, требуется явная миграция: указать нового допустимого родителя или исключить экземпляр из версии контента. Если ближайший сохранённый предок присутствует, новому предмету назначается указанный начальный родитель. Итоговая локация определяется по текущей цепочке размещения.

## Журнал и транзакция действий

`seq` задаёт порядок зафиксированных записей. Для действия с игровыми изменениями `ordinal = 0` хранит итоговый результат и текст ответа. Последующие записи описывают сработавшие правила с `rule_id`, включая значимые изменения, например новое размещение. Для `once: true` ключом `once_key` служит ID правила и действует на всё прохождение. Для повторяемого правила поле остаётся `NULL`. Перемещения, состояние, знания, посещения, игровой шаг и журнал фиксируются одним `COMMIT`. [Транзакции SQLite](https://www.sqlite.org/lang_transaction.html)

1. Интерфейс структурирует ввод и присваивает команде `action_id`. При повторе той же команды после сбоя сохраняется тот же ID. В транзакции движок проверяет запись `(action_id, 0)` и, если она уже есть, возвращает сохранённый результат.
2. Движок разрешает цель, проверяет восприятие, доступность и условия на актуальном состоянии. Если действие отклонено, транзакция откатывается. В начальном режиме команды одного сохранения обрабатываются последовательно.
3. Движок применяет основной эффект и подходящие локальные правила. Перед одноразовым эффектом проверяет `once_key`. При ошибке эффекта откатывается всё действие, включая регистрацию цели в другой локации и метку одноразовости. Эффекты, запускаемые движком, используют тот же исполнитель операций и ту же транзакцию.
4. Успешная команда с затратой времени увеличивает `step` один раз. Для первого сценария `open`, `take`, `go` и `search` стоят один шаг. Осмотр может сохранять новое знание без увеличения шага. Инициализация строк сама по себе не считается игровым изменением.
5. Движок записывает результат значимого действия, правила и изменения в одной транзакции. Успех сообщается только после фиксации. Если итог фиксации неизвестен, движок сначала проверяет журнал по `action_id`. Повтор всей транзакции допустим после подтверждения отсутствия результата. Чистое чтение можно повторить.

## От YAML к сохранению и обратно

| Момент | Ящик `obj.entry.box` | Тетрадь `obj.entry.book` |
| --- | --- | --- |
| Первая сборка сцены | Регистрация с `is_open: false`, родитель `location.demo.entry`. | Определена в каталоге, будет зарегистрирована при обращении к содержимому. |
| Игрок открывает ящик | `is_open: true`. Одноразовое правило регистрирует и открывает `obj.store.door`, даже если кладовая ещё не посещена. | Становится доступна, при чтении содержимого регистрируется с родителем `obj.entry.box`. |
| Игрок берёт тетрадь | Остаётся открытым. | Тот же ID, новый родитель `actor.player`. |
| Повторный вход или загрузка | Читается сохранённое `is_open: true`. | Читается родитель `actor.player`, поэтому в ящике тетрадь не появляется. |

В этот момент новый YAML-предмет в ящике получит начального родителя `obj.entry.box`. Лежащий там ключ и вынутая тетрадь сохранят собственное состояние и размещение.

## Изменения контента и схемы

- Добавление ID с допустимым родителем, переименование отображаемых имён и правка текстов совместимы с сохранением. Порядок файлов не влияет на состояние.
- Изменение `initial` применяется при будущей регистрации. Если нужно поменять уже сохранённое состояние, требуется миграция.
- Перенос файла без изменения определений совместим. Изменение начального родителя существующего определения влияет на будущую регистрацию, а уже сохранённое размещение сохраняется. Перенос экземпляров в существующих сохранениях требует миграции, как и изменение источника или назначения опубликованного перехода, если от него зависит прогресс.
- Отсутствующее определение присутствующего экземпляра, замена его типа или изменение набора сохранённых полей требуют явной миграции. Удалённый экземпляр может остаться в SQLite без YAML-определения, сохраняя ID. Удалить тип из каталога можно после миграции или удаления зависимых присутствующих экземпляров и правки всех ссылок в YAML.
- Идентификаторы не переиспользуются. Переименование выпущенного ID или изменение смысла одноразового правила требует решения о переносе ссылок, истории и меток одноразовости.
- `schema_version` описывает формат входного YAML. `PRAGMA user_version` описывает схему базы. Загрузчик проверяет совместимость формата, индекса и сохранения до начала игры, в том числе допустимость сохранённых родителей по текущему составу компонентов. Несовместимые редакции контента требуют отдельной процедуры миграции.
