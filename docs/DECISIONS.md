# Архитектурные решения

## Исходные требования

- Мир описывается YAML. У локации один самостоятельный файл, у обычных предметов общий каталог типов и универсальные компоненты.
- Сущности имеют глобальные неизменяемые ID. Переходы направлены. Перенос предмета сохраняет его ID.
- SQLite хранит актуальное состояние, размещение, знания и журнал. Повторная инициализация сохраняет существующие значения.
- Действия и события используют общий механизм. Изменения и журнал фиксируются атомарно.
- Игровые правила независимы от интерфейса. Первый интерфейс локальный.

## Решения черновика

| Решение | Предлагаемая модель и основание |
| --- | --- |
| Композиция | Плоский набор компонентов. Переопределения меняют только объявленные поля. Начальные значения предсказуемы и видны в каталоге и экземпляре. |
| Размещение | Одна связь с родителем по ID. Один запрос даёт непосредственное содержимое, перенос контейнера сохраняет целое поддерево. |
| Регистрация | Глобальный индекс проверяется при запуске. Состояние создаётся при обращении, выборка сцены использует сохранённое размещение. |
| Состояние | ID, существование и размещение в реляционных столбцах. Изменяемые поля компонентов в типизированном JSON. Статические параметры берутся из утверждённой при запуске редакции YAML. |
| Восприятие | Детерминированное обнаружение и отдельно сохранённые знания. Условия и размещение определяют текущую видимость. |
| События | Последовательная транзакция на действие, один журнал с ключом команды и ключами одноразовых правил. Межлокационная цель разрешается по ID. |

## Вопросы к утверждению

| Вопрос | Рекомендация |
| --- | --- |
| Нужно ли наследование типов? | Утвердить композицию и переопределения полей. Вернуться к переиспользуемым наборам после появления повторяющихся типов. |
| Где хранить инвентарь и вложенность? | Утвердить одного родителя по ID и проверку циклов в транзакции. Ограничения по весу, стеки и отдельные слоты проектировать при появлении соответствующих механик. |
| Какие поля сохранять? | Сохранять все изменяемые поля по схеме компонента. Характеристики, которые часто нужны в SQL-запросах, выделять в столбцы по мере необходимости. Связь поломки с открытостью, замком, сохранностью содержимого и существованием предмета согласовать до появления эффекта поломки в контенте. |
| Как удалять типы и переносить существующие определения? | Прерывать открытие несовместимого сохранения с понятной диагностикой. Явной миграцией менять размещение или тип живых экземпляров и сохранять удалённые ID для истории. |
| Что версионировать? | Начать с `schema_version: 1` для YAML и `user_version = 1` для БД. Утвердить идентификатор редакции контента и способ версионирования миграций перед первой несовместимой редакцией мира. До этого менять опубликованные ID и топологию только через согласованную миграцию. |
| Как расширять условия и эффекты? | Начать с конъюнкции типизированных условий и упорядоченного списка эффектов. Дополнять операции по сценариям. Согласовать триггеры вне действий игрока, если появятся таймеры в игровых шагах. |
| В какой области срабатывает локальное событие? | Использовать локацию, где началось действие. Для последующих сценариев с переносимыми триггерами обсудить явную привязку события к экземпляру. |
| Когда увеличивать шаг? | В первом срезе сдвигать шаг при успешных действиях с затратой времени. Детерминированный осмотр и повторный ввод после сбоя не продвигают время без нового действия. |
